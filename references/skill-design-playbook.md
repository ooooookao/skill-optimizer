# Skill 设计手册

> 何时读：设计新 skill 或优化现有 skill 时查阅。速查表格式，按场景查表。

---

## 设计哲学

| 原则 | 说明 |
|------|------|
| 实战优先 | 用户关心输出质量，不关心文件结构。测试 5 分钟 > 文档 2 小时 |
| 行为驱动 | 告诉 agent "做什么"而非"是什么"。形容词无法推导行为 |
| 用户选择 | 策略性决策交给用户，agent 只提供选项和利弊 |
| 迭代常态 | 生成 → 展示 → 确认 → 改进 → 交付，不追求一次到位 |

---

## 文件组织速查

| 文件 | 放什么 | 何时读 |
|------|--------|--------|
| SKILL.md | 全局规则 + 工作流导航 + 触发条件 | 每次必读 |
| steps/stepN-*.md | 详细操作指南 + checklist | 执行到该步才读 |
| references/*.md | 速查表（表格/列表，非教程） | 用到才读 |
| assets/templates/* | 模板骨架（含占位符和说明） | 用到才读 |
| examples/* | 完整示例 | 用到才读 |
| scripts/* | 工具脚本 | 用到才读 |

**判断标准**：不是每次执行都需要的内容，不该放 SKILL.md。

## SKILL.md 必含项

1. **Frontmatter** — `name` + `description`（决定触发准确率）
2. **核心原则** — 3-5 条
3. **工作流导航** — 每步一行 + ✓ 最低要求
4. **全局规则** — 输出格式、质量底线、熔断
5. **资源索引** — 文件列表 + "何时读"

### Frontmatter 写法

```yaml
---
name: skill-name
description: >-
  一句话说明做什么。
  触发条件1：用户说"XXX"时触发。
  触发条件2：用户提供YYY时也应触发。
---
```

太宽泛→误触发，太窄→漏触发。

## Step 文件模板

```markdown
---
step: N
title: 做XX
---
# Step N: 做XX
## 执行清单
- [ ] 步骤1
- [ ] 步骤2
## 详细操作
### 1. 步骤1的具体做法
> 如需参考资料，查阅 `references/xxx.md`
```

## Reference 文件模板

```markdown
# 速查标题
> 何时读：XXX 时查阅。
---
## 场景 → 做法
| 场景 | 做法 | 注意 |
|---|---|---|
| 情况A | 处理方式A | 易错点 |
```

原则：agent 不需要"为什么"，只需"怎么做"和"出错怎么办"。

## 强制拦截（Gate）设计原则

Agent 天然倾向"快速给结果"，会跳过耗时步骤。设计 skill 时必须在关键节点加硬性拦截。

**哪些节点必须加 Gate：**
- 用户确认点（确认后才能执行）
- 并行任务汇聚点（全部完成才能继续）
- 质量检查点（通过才能保存/交付）
- 循环体入口（上一轮分析完才能开始下一轮）

**Gate 写法模板：**

```markdown
### ⚠️ 通过条件（Gate）

**[说明为什么不能跳过]** 自检：

- [ ] [条件1]？
- [ ] [条件2]？
- [ ] [条件3]？

**任何一项未完成 → 不能进入下一步。**
```

**关键原则：**
- Gate 必须用 `⚠️` 标记，让 agent 一眼看到
- Gate 必须写"不能进入 XX"，不能只写"建议完成"
- Gate 的条件必须是可验证的（✓/✗），不能是模糊的"是否合理"
- Gate 放在 step 文件末尾（靠近下一步的入口）

## 质量保障速查

| 机制 | 做法 |
|------|------|
| 评分双层面 | 质量（做得好不好）+ 风险（会不会出问题） |
| 分级处理 | 优秀→交付 / 可用→改进一次 / 较差→熔断 |
| 确认前置 | 先展示结果让用户确认方向，再做质量检查 |
| 熔断机制 | 3 次改进仍不达标 → 暂停，向用户报告，提供选项 |

## 优化工作流速查

```
生成 v1 → 展示 → 用户确认 → 检查 → 改进 → 重测 → 交付
```

### 修复优先级（按影响范围）

1. **控制层** — 影响所有轮次的指令
2. **基础层** — 影响基本行为的字段
3. **输出层** — 影响格式质量的指令
4. **触发层** — 影响触发条件的设置

### 重测原则

用**同样的测试场景**重测，不要换场景。

## 子 Agent 设计原则

复杂 skill（≥5 步 / 并行任务 / 大量文件处理）应使用子 agent，主 agent 专注协调：

| 谁 | 职责 |
|---|---|
| **主 agent** | 协调流程、用户交互、路由决策、状态管理、汇总结果 |
| **子 agent** | 执行具体任务（分析、生成、提取、搜索）、并行处理、隔离上下文 |

**什么时候该用子 agent：**
- 多个独立任务可并行（如 4 个维度同时提取）
- 单任务输出量大，会撑爆主 agent 上下文
- 需要独立上下文避免污染主流程
- 故障隔离：子 agent 挂了不影响主流程

**什么时候不用：**
- 简单的单步操作
- 需要用户交互的任务
- 需要主对话上下文的任务

**⚠️ 子 agent 调用后必须有 Gate：**

每个子 agent 返回后，主 agent 必须验证输出才能继续。Gate 内容：

```markdown
### ⚠️ 子 agent 返回后验证（Gate）

- [ ] 子 agent 是否成功返回？（未成功 → 重试/降级，见 references/sub-agent-strategy.md）
- [ ] 输出文件是否已生成？
- [ ] 输出内容是否完整？（非空、格式正确、无明显错误）
- [ ] 输出是否符合预期？（抽样检查关键字段）

**验证不通过 → 重试或降级，不能跳过直接用。**
```

为什么必须有：
- 子 agent 可能静默失败（返回了但内容不完整）
- 子 agent 可能格式错误（输出了但格式不对）
- 子 agent 可能偏离任务（返回了但内容不对）
- 没有 Gate 的话，主 agent 会直接拿错误输出继续往下走

---

## 子 Agent 使用速查

| 场景 | 用子 agent | 用主 agent |
|------|-----------|-----------|
| 并行独立任务 | ✅ | ❌ |
| 隔离上下文 | ✅ | ❌ |
| 简单单步操作 | ❌ | ✅ |
| 需要用户交互 | ❌ | ✅ |
| 需要主对话上下文 | ❌ | ✅ |

### Prompt 要素

角色定义 + 任务描述 + 输入数据 + 输出格式 + 约束条件。**必须自包含**（子 agent 无主对话上下文）。

### 故障处理

第 1 次 → 立即重试 / 第 2 次 → 等 5s / 第 3 次 → 等 15s / 3 次失败 → 主 agent 降级执行

## Token 优化速查

| 方法 | 说明 |
|------|------|
| SKILL.md 精简 | 只放"每次都需要"的内容 |
| 参考资料用表格 | 表格 > 列表 > 段落 |
| 不跨文件重复 | 一处定义，其他引用 |
| 示例精简 | 一个高质量 > 三个平庸 |
| 删解释留操作 | "怎么做"留，"为什么"删 |

**检验标准**：删除某段内容后 skill 仍能正常工作 → 那段内容不该存在。

## 工作区权限自动配置

设计新 skill 时，如果它需要调用工具（Bash、Read、Write 等），应内置工作区权限配置流程，避免用户反复点击确认弹窗。

### 流程模板

在 SKILL.md 中加入：

```markdown
## 工作区权限配置

首次运行时执行：

1. **确认工作区** — 询问用户目标目录（已提供则跳过）
2. **询问是否自动配置权限** —
   > 这个 skill 需要使用 [工具A]、[工具B] 等工具。要自动把这些工具的权限配好吗？
   > 配好后后续运行不会反复弹确认框。权限随时可在 settings.json 中收回。
   > - 是，自动配置
   > - 不，逐个确认
3. **用户选"是"** → 读取 `.claude/settings.json`，合并写入 `permissions.allow`
4. **用户选"否"** → 正常运行，逐个确认
```

### settings.json 写入格式

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Read(*)",
      "Write(src/**)",
      "Edit(src/**)"
    ]
  }
}
```

### 设计原则

| 原则 | 说明 |
|------|------|
| 最小权限 | 只加该 skill 实际用到的工具，不全开 |
| 合并写入 | 先读已有配置，追加而非覆盖 |
| 可收回 | 告知用户随时可手动修改 settings.json |
| 敏感操作二次确认 | `rm`、`git push`、`DROP` 等即使有权限也应 skill 内部确认 |

## 经验积累机制（越用越聪明）

设计 skill 时应内置经验积累机制，让 skill 随使用次数增加而变得更准、更快、更贴合用户。

### 四种模式

| 模式 | 适用场景 | 实现方式 | 参考案例 |
|------|----------|----------|----------|
| **经验库文件** | 跨项目复用的知识 | `references/experience.md` 或 `experience/` 目录，每次运行后追加 | auto-tuner：调参经验跨项目复用 |
| **知识库增长** | 可复用的素材/模板 | `assets/xxx-library.json`，用脚本导入/导出 | tavern-card-gen：world-library.json 越用越大 |
| **历史记录** | 追踪趋势、对比版本 | `.optimizer_history/` 或 `history.json`，每次运行记录 | skill-optimizer：优化历史追踪 |
| **反馈循环** | 用户修正后自动学习 | 记录用户修改 → 下次运行时参考 | novel-continuation：progress.md 记录用户反馈 |

### 设计模板

在 SKILL.md 或 step 文件中加入：

```markdown
## 经验积累

每次运行结束后：
1. 提取本次关键发现（什么有效、什么无效）
2. 追加到 `references/experience.md`（或对应的经验文件）
3. 下次运行时先读取经验库，参考历史经验调整策略

经验格式：
| 日期 | 场景 | 发现 | 适用条件 |
|------|------|------|----------|
| 2026-06-01 | XX项目 | lr=0.001 效果最好 | 数据量<10k时 |
```

### 设计原则

| 原则 | 说明 |
|------|------|
| 追加不覆盖 | 经验只增不删，保留历史 |
| 结构化存储 | 用表格/JSON，不用自由文本，方便检索 |
| 带上下文 | 每条经验标注适用条件，避免误用 |
| 跨会话持久 | 写入文件而非依赖对话记忆 |
