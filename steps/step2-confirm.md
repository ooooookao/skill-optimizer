# Step 2: 方案确认

**目的**：向用户展示完整报告 + 修改计划，确认修改范围。
**前置**：Step 1 完成（分析 + 调研报告已生成）。
**输出**：用户确认的修改范围。

---

## 执行清单

- [ ] 展示合并报告（问题清单 + 调研发现 + 失败模式分类）
- [ ] 给出修改计划（哪些问题怎么改）
- [ ] 用户确认修改范围
- [ ] 同行评审（仅完整模式；快速模式跳过）
- [ ] 进入 Step 3（仅完整模式；快速模式在此结束）

---

## 详细操作

### 1. 展示合并报告

将 Step 1 的两路结果整合展示：

```
═══ 分析报告 ═══

总分: XX/100 — [等级]
  结构分: XX/60（自动检查）
  内容分: XX/40（LLM 评估）

问题清单（含失败模式分类）：
| 严重程度 | 类别 | 问题 | 失败模式 |
| [严重] | 架构 | SKILL.md 350行，应拆到 steps/ | universal |
| [高] | 质量 | 缺少熔断机制 | universal |
| [中] | Token效率 | references/xxx.md 不是速查表格式 | regression |
| [低] | 体验 | 没有 examples/ 目录 | model-specific |

═══ 调研发现 ═══

竞品矩阵：
| 产品 | 定位 | 核心优势 | 核心短板 |
| ... | ... | ... | ... |

竞品经验：
- 竞品A 的用户最需要：[功能X]
- 市场空白：[功能Y]

═══ 优化方向 ═══

| 优先级 | 方向 | 理由 | 参考竞品 |
| P0 | [方向1] | 竞品A用户最需要 | 竞品A |
| P1 | [方向2] | 市场空白 | 竞品B |
```

### 2. 给出修改计划

针对每个问题，给出具体可执行的修改方案：

```
修改计划：

1. [严重] SKILL.md 350行 → 拆分到 steps/ 和 references/
   方法：运行 fix_skill.py 自动拆分

2. [高] 缺少熔断机制 → 在 SKILL.md 添加熔断规则
   方法：参考 skill-design-playbook.md 的熔断模板

3. [中] references/xxx.md 不是速查表 → 改为表格格式
   方法：手动重写

4. [低] 没有 examples/ → 创建目录
   方法：fix_skill.py 自动创建
```

### 3. 用户确认修改范围

```
你想改哪些？
1. 全部改（推荐）
2. 只改严重和高危问题
3. 指定具体问题
```

用户确认后进入同行评审（仅完整模式）。

**快速模式**：展示报告后直接结束，告知用户"如需执行修改，请用完整模式重新运行"。

**用户也可能说**：
- "先不动了" → 结束，保留报告
- "调研结果有问题" → 重新确认调研范围，回到 Step 1 右路
- "这些问题哪些最重要？" → 按优先级分析后重新确认

### 4. 同行评审（方案验证）⚠️ 仅完整模式，不可跳过

用户确认修改范围后，**必须**启动 2 个子 agent 正反辩论，验证方案是否合理。不能因为"用户已经确认了"就跳过。

辩论模板详见 `references/peer-review-debate.md`。

- 正方：论证修改方案合理，可以执行
- 反方：找出方案中的问题（遗漏、过度修改、优先级错误）

综合两方观点后向用户展示评审结果：
- 通过 → 进入 Step 3 执行
- 有问题 → 先修方案再执行，或回到 Step 2 重新确认

### ⚠️ 通过条件（Gate）

**同行评审通过后才能进入 Step 3。** 自检：

- [ ] 报告已展示给用户？
- [ ] 用户已确认修改范围？
- [ ] 同行评审已完成（正反两方都返回）？
- [ ] 正方论点是否具体？（不能只说"方案合理"，要列出具体理由）
- [ ] 反方论点是否具体？（不能只说"没问题"，要列出检查过的维度）
- [ ] 正反方是否有实质性分歧？（如果两方完全一致，可能是评审不够深入）
- [ ] 综合结论是否明确？（通过/有条件通过/不通过，不能模糊）
- [ ] 评审结果已展示给用户？

**任何一项未完成 → 不能进入 Step 3。**
