# Step 3: 执行修改 + 评分验证

**目的**：按确认的方案执行修复，评分验证，不通过则回路。
**前置**：Step 2 完成（用户已确认修改范围）。
**输出**：优化后的 skill + 评分报告。

---

## 执行清单

- [ ] 3.1 dry-run 预览修复计划
- [ ] 3.2 执行自动修复
- [ ] 3.3 手动修复内容质量问题
- [ ] 3.4 补充 README / 经验积累 / 工作区权限（如缺失）
- [ ] 3.5 展示变更摘要 + 前后对比
- [ ] 3.6 运行质量门禁评分（四态判定）
- [ ] 3.7 同行评审（2 个子 agent 正反辩论最终审查）
- [ ] 3.8 Cycle Boundary（循环边界：PASS→交付 / CONCERNS→确认 / BLOCK→回路 / 超限→决策）
- [ ] 3.9 记录历史

---

## 详细操作

### 3.1 dry-run 预览

```bash
python scripts/fix_skill.py <skill目录路径> --dry-run
```

向用户展示修复计划，确认后再执行。

### 3.2 执行自动修复

```bash
python scripts/fix_skill.py <skill目录路径>
```

脚本自动修复：
- 创建缺失的目录（steps/references/examples）
- SKILL.md 过长 → 拆分到 reference 文件
- step 文件缺少 checklist → 从 ### 标题自动生成
- step 文件缺少 frontmatter → 自动生成

### 3.3 手动修复内容质量问题

不能自动修的（内容质量问题），由 agent 手动修改：
- description 触发条件有歧义 → 重写 description
- step 操作指南不清晰 → 补充具体操作步骤
- reference 内容不准确 → 修正内容
- 跨文件重复 → 删除重复段落，改为引用

### 3.4 补充缺失组件

**README 补充：**
- 缺少 README.md → 自动生成骨架
- README 存在但内容过少 → 基于 SKILL.md 补充
- README 描述与项目不同步 → 手动更新过时部分

**经验积累机制补充：**
- 缺少 → 根据 skill 类型选择模式（见 `references/skill-design-playbook.md` 的"经验积累机制"）
- 不完善 → 补充结构化格式

**工作区权限配置：**
- 缺少 → 在 SKILL.md 或 Step 0 中添加权限配置段落
- 有 → 跳过

**强制拦截（Gate）补充：**
- 关键节点缺少 Gate → 在 step 文件末尾添加 `⚠️ 通过条件（Gate）` 段落
- 需要加 Gate 的节点：用户确认点、并行任务汇聚点、质量检查点、循环体入口
- 每次子 agent 调用后必须有验证 Gate（检查成功/输出完整/格式正确）
- Gate 写法见 `references/skill-design-playbook.md` 的"强制拦截（Gate）设计原则"和"子 Agent 设计原则"

### 3.5 展示变更 + 前后对比

```
变更摘要：
| 修改项 | 旧状态 | 新状态 |
|---|---|---|
| SKILL.md | 350行 | 180行 |
| steps/step1.md | 无清单 | 添加5项清单 |
| 新增 | 无 | references/xxx.md |

前后对比：
| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 总分 | 62 | 88 | +26 |
| 结构分 | 48/60 | 56/60 | +8 |
| 内容分 | 14/40 | 32/40 | +18 |
| 严重问题 | 2 | 0 | -2 |
| 高危问题 | 3 | 1 | -2 |
| 门禁 | FAIL | PASS | - |
```

### 3.6 运行质量门禁

```bash
python scripts/quality_gate.py <skill目录路径>
```

### 3.7 同行评审（最终审查）⚠️ 不可跳过

门禁通过后，**必须**启动 2 个子 agent 正反辩论，做最终审查。不能因为"门禁已经过了"就跳过。

辩论模板详见 `references/peer-review-debate.md`。

- 正方：论证修改后的 skill 可以交付
- 反方：找出遗留问题（跨文件不一致、逻辑 bug、遗漏场景）

综合两方观点后向用户展示评审结果：
- 通过 → 进入 3.8 交付
- 有问题 → 列出问题，问用户修还是不修

### ⚠️ 3.7 同行评审验证（Gate）

同行评审完成后，**必须**验证输出质量才能进入 3.8：

- [ ] 正方 agent 是否成功返回？
- [ ] 反方 agent 是否成功返回？
- [ ] 正方论点是否具体？（不能只说"可以交付"，要列出检查过的维度和结论）
- [ ] 反方论点是否具体？（不能只说"没问题"，要列出检查过的维度）
- [ ] 正反方是否有实质性分歧？（两方完全一致 → 评审不够深入，需重新评审）
- [ ] 综合结论是否明确？（通过/有条件通过/不通过）
- [ ] 遗留问题是否已列出？（有条件通过时必须列出具体问题）

**验证不通过 → 重新启动同行评审（换 prompt 或换角度），不能跳过直接进入 3.8。**

### 3.8 Cycle Boundary（循环边界）

本轮修复完成，运行质量门禁，根据四态结果决定下一步。

**初始化**：设置 `cycle_count = 0`，`max_cycles = 3`。

**每轮循环**：
1. 运行 `quality_gate.py` 获得四态结果
2. `cycle_count += 1`
3. 根据状态分支：

**PASS → 交付**
- 展示最终报告
- 告知用户"优化完成，所有指标达标，同行评审通过"

**CONCERNS → 展示警告，用户确认**
- 展示警告列表（仅 low/medium 问题）
- 用户确认后交付
- 用户不确认 → 回到 3.2 继续修复

**BLOCK + cycle_count < max_cycles → 自动回路**
- 展示阻塞项
- 自动回到 3.2 继续修复
- 告知用户"还有阻塞问题，自动进行第 N 轮修复"

**BLOCK + cycle_count ≥ max_cycles → 强制决策点**

```
已达最大循环次数（3轮），仍有阻塞问题：
  [BLOCK] 高危问题: 2（要求 ≤2）
  [BLOCK] 总分: 72（要求 ≥75）

你想怎么处理？
1. 继续改（重置循环计数，再跑 3 轮）
2. 重新走方案设计（回到 Step 2）
3. 豁免阻塞项（WAIVED，记录原因后交付）
4. 放弃优化（保留原样）
```

- 选项 1 → 重置 cycle_count = 0，回到 3.2
- 选项 2 → 回到 Step 2，重新展示报告 + 修改计划
- 选项 3 → 运行 `quality_gate.py --waive`，记录豁免原因，交付
- 选项 4 → 结束，不修改任何文件

### 3.9 记录历史

修复完成后，记录到 `.optimizer_history/`，用于趋势追踪。
